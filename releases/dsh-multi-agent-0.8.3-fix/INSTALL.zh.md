# DSH 多 Agent 派发 0.8.3 — 安装与安全说明

这是本地分享试用包，不是 DSH 官方插件，也未发布到 npm / GitHub。

## 一、准备环境

1. DSH 必须为 `0.2.2-rc.1` 或 `0.2.2-rc.2`；其它版本未列入兼容范围，不要通过版本豁免强行安装。
2. 在自己的 DSH 中配置可用模型。仅使用 DSH 子代理时，不需要安装外部 CLI。
3. 需要哪个外部 Agent，就在本机安装并登录哪个 CLI：Codex、Kimi Code 或 Google Antigravity（agy）。安装这个插件不会赠送账号、模型额度，也不会带入分享者的登录。
4. 如需右侧“Agent 任务”面板，先通过 DSH 插件管理器安装并启用兼容当前 DSH 的 `dsh-better-sidebar`。这是独立扩展，本包未捆绑；没有它不应期待本插件 Client 界面完整加载。
5. 安装依赖需要联网。macOS 是打包与回归验证平台；Linux / Windows 未经过实机安装和 CLI 执行验收。

## 从 0.8.2 更新到 0.8.3

本版是 Codex 导入链的最小修复候选，不需要删除用户配置或逐个安装 `dsh-util-time` 等宿主 peer。

1. 备份自己的插件设置，通过 DSH 插件管理器替换安装包。如果管理器提示 already-installed 并要求卸载，先卸载本插件 bundle，再安装新的 TGZ；不要清空整个 profile。
2. 完全退出并重新启动 DSH，确认管理器显示 0.8.3，再查看 Codex 组件是否仍有加载错误。
3. 若能启用，再做一次小型 Codex 委派。若仍失败，请取得 **DSH Host 的完整 failed to import 异常与 cause**，不要再以普通 Node 的缺 peer 输出替代它。

DSH 默认关闭 peer 自动安装，并由宿主提供依赖解析。普通终端的 Node 没有这层机制，可能报告 Host 实际能够提供的包缺失。本版只消除了 Codex 不必要的宿主服务加载链，不宣称已完成 Windows Host 验收。

## 二、首次安装（推荐）

收到外层分享 ZIP 后先解压，里面的 `local-dsh-multi-agent-0.8.3.tgz` 才是插件安装包。不要把外层 ZIP 当作插件传给安装器，也不必先解开 TGZ。

把 TGZ 文件或它在 DSH 所在电脑上的绝对路径交给 DSH，并发送：

> 请安装我提供的本地多 Agent 派发插件 TGZ。先检查我的 DSH 版本、安装包信息和 Better Sidebar 前置依赖，再通过插件管理器安装。不要手动改 profile 文件，不要开启版本豁免，不要自动把 Kimi/agy 权限从 reject 改成 allow。如果需要执行依赖安装脚本，先说明具体脚本和原因。安装后核验插件状态，并按管理器返回结果告知是否需要重启。

对应 DSH 工具是 `plugin_manager` 的 `install_bundle` 操作，`target` 使用本地 TGZ 的绝对路径（也支持绝对 `file:` tarball spec）。不要在 profile 目录手工执行 npm / pnpm 安装。

管理器若返回需要重启，就重启 DSH；若返回已应用，仍要检查设置页、任务面板和测试任务。仅看到磁盘文件或包版本不代表新模块已生效。

**如果已安装同名 `@local/dsh-multi-agent`：** 先备份自己的插件设置，遵循管理器的升级结果。旧版管理器可能要求先卸载再安装；不要盲目卸载、复制整个 profile 或覆盖其它插件配置。

## 三、首次配置

打开 DSH 设置中的“多 Agent 派发”：

- 先用 DSH 自身做一个小任务确认基础能力，再启用需要的外部 Agent。
- 模型/推理强度可留空继承后端默认；只填写自己账号可用的模型。
- 根据需要调整自然语言路由。插件会向主会话添加主动派发指引，并对部分原生新建委派工具施加工作流约束，影响当前 profile 中可使用该插件的主会话，不只是一个面板装饰。
- CLI 缺失时对应 Provider 不启用；向不可用外部 Agent 派发可能回退 DSH，工具回执会说明 fallback。请检查实际执行者，不要以为始终由指定外部 CLI 完成。

### CLI 路径

- Codex：搜索 PATH 和已支持的常见安装位置；可用启动环境变量 `CODEX_COMMAND` 指定路径。
- Kimi：优先检测当前用户的 `~/.kimi-code/bin/kimi`，再搜索 PATH；可用 `KIMI_COMMAND` 指定路径。
- agy：优先检测当前用户的 `~/.local/bin/agy`，再搜索 PATH；可用 `AGY_COMMAND` 指定路径。

这些变量必须进入 **DSH 进程的启动环境**。在另一个终端里临时 export，不会改变已运行桌面进程的环境。自定义命令也可在插件设置中填写；若安装位置无法被自动检测，需要同时解决启动检测路径。新装 CLI 后通常需要重启或重载插件。

## 四、权限与费用：先读再启用

- **Kimi / agy 新安装默认 `permission: reject`。** 插件会拒绝 ACP 发出的权限请求；读文件、执行任务或写报告是否被拒绝，取决于 CLI 的请求方式。任务失败时应先查看诊断，不要把缺失报告当作成功。
- 只有理解并接受风险、且工作区可信时，才由用户在设置中改成 `allow`。`allow` 会自动批准 ACP 支持的授权选项，可能允许写文件、执行命令及访问 CLI 自身可访问的内容。
- `reject` **不是操作系统级沙箱**，也不保证 CLI 的所有行为都会请求权限。敏感工作应使用独立工作目录、容器或其它隔离方式。
- Codex 默认 `approve-for-me`，使用其自动审查及 workspace-write 策略，不是逐项人工确认，也不是只读。不要无必要地改成绕过审批和沙箱。
- DSH、Codex、Kimi、agy 使用各自的模型配置、登录和计费。多个 Agent 并行可能同时消耗额度。
- 父 DSH 的权限设置不等于所有外部 CLI 自动继承相同权限。安装本插件不代表授予所有后续操作无限权限。

本包不包含分享者的账号、密钥、会话历史、任务报告、备份或 node_modules。首次安装仍会从配置的包仓库下载 npm 依赖；它不是离线全依赖包。

## 五、安装后检查

1. 插件管理器未显示加载失败；设置页可打开。
2. 如已安装 Better Sidebar，可打开“Agent 任务”面板。
3. 给 DSH 一个小型只读分析任务，确认派发回执、最终通知和任务状态一致。
4. 按需测试已登录的外部 CLI。若需要写报告，应事先选择自己接受的权限策略，不要为了测试直接关闭所有安全限制。
5. 测试已完成任务的续接，确认沿用原任务，而不是创建另一份会话。

## 六、兼容性与数据提醒

插件沿用 rc.1 / rc.2 双版本兼容层，测试覆盖两版接口及官方固定源码的隔离契约。**这不等于在所有系统、CLI 版本、第三方侧栏组合上完成了端到端验收；rc.2 桌面完整验收仍有限制。**

DSH rc.2 创建具名子代理后可能写入 rc.1 无法读取的会话记录。升级 DSH 前备份自己的会话存储，不要让两版进程同时读写同一份存储，也不要直接在新版记录上降级。
